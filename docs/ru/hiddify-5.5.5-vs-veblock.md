# Hiddify 5.5.5 и Veblock: возможности и приоритеты развития

Дата сравнения: 9 ноября 2026 года. Состояние Veblock — исходники на коммите
`687fb57`; возможности установленной сборки могут отличаться.
Hiddify оценивается по официальным описаниям, Veblock — по коду и ближайшим тестам.
Это анализ реализации, без сравнительных запусков и сетевых испытаний.

Главный разрыв — запас способов подключения при блокировках и удобство выбора
рабочего сервера. Базовые возможности Veblock уже позволяют улучшать эти сценарии
без немедленного добавления второго ядра.

## Где Veblock уступает

| Область | Veblock сейчас | Разрыв относительно Hiddify |
| --- | --- | --- |
| Альтернативные подключения | Xray: VLESS, Trojan, VMess, Shadowsocks, SOCKS, HTTP и Hysteria2 | Нет готовых сценариев DNS-туннелей, Psiphon и встроенного WARP с выбором транспорта |
| Качество серверов | Пакетная проверка задержки, сортировка по пингу | Нет полноценного теста загрузки и отдачи каждого сервера |
| Большие подписки | Группы, поиск, сортировка, пакетные проверки | Нет сопоставимого выбора лучших N и рабочего набора с фильтрами по результатам |
| Причины отказов | Мониторинг, ошибки подключения, отдельная диагностика сети | Не хватает сохранённой причины и времени проверки непосредственно у каждого сервера |
| Цепочки | Интеграция с системным VPN, включая туннели WireGuard на Windows, и маршрутизация | Это не готовые цепочки с WARP/Psiphon перед или после основного прокси |
| Другие устройства | Готового сценария LAN-раздачи с QR-кодом в исследованном коде не найдено | В Hiddify он оформлен в интерфейсе |
| Платформы | Linux и Windows | У Hiddify также есть Android, macOS и сценарии Android TV |

Возможности Hiddify подтверждены [релизом 5.5.5](https://github.com/hiddify/hiddify-app/releases/tag/v5.5.5)
и [журналом изменений](https://github.com/hiddify/hiddify-app/blob/v5.5.5/HISTORY.md).
Наличие дополнительных протоколов само по себе не гарантирует подключение в конкретной сети.

## Что уже реализовано в Veblock

| Возможность | Основание в репозитории |
| --- | --- |
| XHTTP и дополнительные параметры | [stream.py](../../src/fmt/stream.py), [тесты](../../tests/test_fmt_xhttp_extra.py) |
| TLS-фрагментация и ряд масок FinalMask | [transport_tweaks.py](../../src/core/transport_tweaks.py), [transport_options.py](../../src/fmt/transport_options.py) |
| Переключение при отказе сервера | [failover.py](../../src/core/failover.py), [контроллер](../../src/ui/controller.py), [тесты](../../tests/test_core_failover.py) |
| Самообновление Windows | [app_update.py](../../src/core/app_update.py), [app_installer.py](../../src/core/app_installer.py), [платформенная реализация](../../src/sys/windows/app_install.py) |
| Проверка рабочей сессии через служебный вход | [health_probe.py](../../src/core/health_probe.py), [monitor.py](../../src/core/monitor.py) |
| Hysteria2 | [hysteria2.py](../../src/fmt/protocols/hysteria2.py), [описание](protocols.md#hysteria2) |
| Туннели WireGuard на Windows (не встроенный WARP) | [wireguard.py](../../src/winsvc/wireguard.py) |
| Отдельная диагностика сети | [модели результатов](../../src/diag/models.py), [описание сценария](../../README.md) |

FinalMask поддерживается частично, включая Sudoku; совместимость конкретных
конфигураций с Hiddify нужно проверять.

Failover учитывает последовательные неудачи, отсутствие сети и недавно отказавшие
серверы. Он уже подключён к контроллеру и настройкам обоих интерфейсов.
Обновление Windows проверяет размер и SHA-256 установщика; на Linux самообновление
[отключено](../../src/sys/linux/app_install.py).

Служебная проверка рабочей сессии обходит пользовательские direct-правила,
чтобы они не создавали ложный успех. Пакетный замер задержки при этом использует
отдельную конфигурацию: успешный пинг не доказывает работоспособность DNS,
маршрутов и TUN рабочей сессии.

## Рекомендуемая очерёдность

Это предложения, а не утверждённый план реализации или обещание сроков.

| Приоритет | Изменение | Проверяемый результат |
| --- | --- | --- |
| 1 | Причины отказов серверов | Время проверки, результат, доступная причина и повторная проверка у сервера; различение ошибок сервера, конфигурации, ядра и системного режима |
| 2 | Тест скорости | Загрузка и отдача выбранных серверов, лимит трафика, отмена, сортировка, явная отметка старых результатов |
| 3 | Рабочий набор подписки и автоматический выбор | Избранные или лучшие N, выбор лучшего при подключении и использование набора существующим failover |
| 4 | Восстановление после смены сети | Проверенные сценарии смены Wi-Fi, сна, потери DNS и службы; видимые этапы и итоговая причина ошибки |
| 5 | Дополнительный способ обхода | Прототип WARP или DNS-туннеля, выбранный по воспроизводимым проблемам пользователей |
| 6 | LAN-раздача и QR-экспорт | Явное включение, пароль, отдельный порт и понятное отключение |

### Первые три улучшения

Для причин отказов можно использовать существующие модели диагностики, сохраняя
различие между наблюдением и предположением. Тайм-аут сам по себе не доказывает
блокировку. Неизвестную причину следует так и обозначать.

Тест скорости должен показывать предполагаемый расход данных до запуска,
выполняться в фоне и корректно отменяться. Измерение через выбранный сервер
и проверка всей рабочей сессии должны оставаться различимыми сценариями.

Veblock не запускает всю подписку постоянно. Поэтому лучшие N должны управлять
выбором, проверками и резервными серверами; обещать такое же снижение нагрузки,
как в Hiddify, без измерений нельзя. Основа: [batch_probe.py](../../src/core/batch_probe.py),
[profiles_view.py](../../src/ui/logic/profiles_view.py) и существующий failover.
Автоматический выбор требует защиты от частых переключений и учёта свежести замеров.

### Архитектурные ограничения

- Второе ядро затронет генерацию конфигурации, Windows-службу, DNS, маршруты,
  обновления и восстановление после сбоев. Это отдельный проект.
- LAN-раздача требует изменения политики: сейчас Windows-служба допускает
  нетуннельные входы только на loopback. Нельзя просто отключить эту проверку:
  см. [policy.py](../../src/winsvc/policy.py).
- Новые пользовательские сценарии нужно проектировать для GTK и Qt вместе,
  согласно [общему дизайну](../plans/2026-11-02-shared-ui-design.md).
- Поддержка дополнительных платформ расширяет область проекта; сейчас полезнее
  завершать сценарии Linux и Windows, чем начинать мобильный порт без отдельного решения.

## Границы выводов и проверки

Изучены исходники и определения целевых тестов, но тесты в рамках сравнения
не запускались. Не измерялись скорость, память, стабильность, поведение под
блокировками и фактическая совместимость протоколов. Проверки установленной
Windows-службы, Linux GUI, D-Bus и TUN не выполнялись.
Оснований объявлять одно приложение более надёжным по этому анализу нет.

См. также [изменения Hiddify между 2.0.5 и 5.5.5](hiddify-2.0.5-vs-5.5.5.md).
