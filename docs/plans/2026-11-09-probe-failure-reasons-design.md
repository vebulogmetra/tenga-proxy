# Причины отказов при замере задержки

Дата: 9 ноября 2026 года. Первый пункт очерёдности из
[сравнения с Hiddify](../ru/hiddify-5.5.5-vs-veblock.md).

## Задача

Замер задержки сводит любой результат к `int`: отказ и «не проверялся» оба
равны `-1` и выглядят как «—». Пользователь не видит, когда сервер проверялся
и почему не ответил; failover не отличает отказавший сервер от непроверенного.

Решение — передавать от пробы до профиля результат с причиной, временем и
текстом ядра. Причины берутся только из того, что код уже наблюдает. Разбор
лога пробного ядра — отдельный следующий шаг, если этого окажется мало.

## Модель

Модуль `src/core/probe_result.py`, без зависимостей:

```python
class ProbeFailure(StrEnum):
    INVALID_CONFIG = "invalid_config"  # build_probe_outbound не собрал outbound
    REJECTED = "rejected"              # xray -test отверг outbound
    CORE_FAILED = "core_failed"        # пробное ядро не запустилось
    TIMEOUT = "timeout"                # requests.Timeout
    UNREACHABLE = "unreachable"        # 5xx от inbound или обрыв соединения
    BAD_RESPONSE = "bad_response"      # 407 и прочие неуспешные ответы

@dataclass(frozen=True)
class ProbeResult:
    latency_ms: int = -1               # > 0 только при успехе
    failure: ProbeFailure | None = None
    checked_at: int = 0                # unix-время, 0 — неизвестно
    detail: str = ""                   # текст ядра или исключения, ≤ 300 символов
```

Конструкторы `ProbeResult.ok(ms)` и `ProbeResult.failed(kind, detail)` ставят
`checked_at` текущим временем.

`ProfileEntry` сохраняет поле `latency_ms` (его читают сортировка, failover,
«Оставить рабочие») и получает `probe_failure`, `probe_detail`, `checked_at`.
Новые ключи пишутся в JSON только непустыми: старые файлы и старая версия
приложения читают профиль как раньше. Неизвестное значение `probe_failure`
читается как `None`. Старый `-1` без причины — «не проверялся».

При изменении `bean` (редактирование сервера) результат сбрасывается: он
относился к прежним параметрам.

Состояния для интерфейса: `failure is not None` — отказ; `latency_ms > 0` —
задержка; иначе — «—», проверки не было.

## Поток данных

`ResultFn` становится `Callable[[int, ProbeResult | None], None]`.

`http_probe.probe_latency` возвращает `ProbeResult`; прежний `measure_latency`
остался обёрткой с `int` для проверки рабочей сессии (`monitor.py`). URL замера —
обычный HTTP, поэтому ответы inbound видны:

- хотя бы один успешный запрос — успех, медиана, как сейчас;
- `requests.Timeout` — `TIMEOUT`: сервер не ответил за время ожидания клиента;
  это не вывод о блокировке;
- `5xx` или `ConnectionError` — `UNREACHABLE`: ядро быстро получило отказ
  при соединении с сервером;
- `407` и иные неуспешные коды — `BAD_RESPONSE`, код в `detail`.

`batch_probe`:

- `build_probe_outbound_or_error` отдаёт и текст исключения — `INVALID_CONFIG` с
  `detail`;
- `core_check` возвращает `(ok, message)`, `message` — последняя содержательная
  строка вывода `xray -test` без звеньев с путём к конфигу и тегом `proxy-N`
  (`core_accepts` остался обёрткой с `bool`). После деления пополам у одиночного
  отвергнутого профиля это его собственная причина — `REJECTED` с `detail`;
- ядро не стартовало после всех попыток — `CORE_FAILED`, в `detail` хвост его вывода;
- неожиданное исключение в `measure_targets` — `UNREACHABLE` с текстом исключения.

`LatencyRunner`: если замер прервался ошибкой нашего кода, профили без
результата получают `None`. Контроллер снимает заглушку «проверяется» и
учитывает прогресс, но прежний результат профиля не трогает: исправный
сервер не должен стать отказавшим из-за сбоя замера.

`failed_profile_ids` работает с `ProbeResult`; условие «хотя бы один ответил»
сохраняется, `None` считается неполным замером.

`AppController._on_latency_result` пишет в профиль все поля; на диск профили
сохраняются, как и сейчас, один раз в `_on_latency_done`.

## Интерфейс

Общая логика — `src/ui/logic/profiles_view.py`: `ProfileRow` получает
`probe_failure`, `probe_detail`, `checked_at`; `ping_text(row)`,
`ping_tooltip(row, now)`, `ping_is_failure(row)`.

| `ProbeFailure` | Метка справа | Первая строка подсказки |
| --- | --- | --- |
| `TIMEOUT` | «нет ответа» | Сервер не ответил за N с |
| `UNREACHABLE` | «нет связи» | Ядро не смогло соединиться с сервером |
| `BAD_RESPONSE` | «ошибка» | Неожиданный ответ при проверке |
| `INVALID_CONFIG` | «ошибка» | Параметры сервера не собираются в конфигурацию |
| `REJECTED` | «ошибка» | Ядро отвергло параметры сервера |
| `CORE_FAILED` | «ошибка» | Не удалось запустить ядро для проверки |

Далее в подсказке — «Проверено: 5 мин назад» (давно — дата) и `detail`, если
есть. У успешного замера подсказка — только время, если оно известно; у «—»
подсказки нет.

Цвет метки отказа — `ERROR_TEXT` из `src/ui/logic/appearance.py`. GTK
(`src/ui/widgets/profile_row.py`): подсказка и CSS-класс `probe-failed` у метки
задержки (цвет Adwaita `.error` отличается от общего). Qt: `Qt.ToolTipRole` и
`PROBE_FAILED_ROLE` в `src/ui/qt/models.py`, цвет и подсказка над плашкой в
`src/ui/qt/widgets/profile_delegate.py`.

Сортировка «По задержке»: успешные по задержке в выбранном направлении, затем
отказавшие, затем непроверенные; последние две группы — по имени в любом
направлении.

В словарь [общего дизайна](2026-11-02-shared-ui-design.md) добавляется: «нет
ответа», «нет связи», «ошибка» — отказ при проверке; «—» — проверки не было.

## Failover

`pick_candidate`: успешные по задержке, затем непроверенные, затем отказавшие.
Сейчас отказавшие стоят наравне с непроверенными.

Обычный pytest, без публичной сети и дисплея:

- `test_core_http_probe.py` — подставная сессия для кодов ответа и исключений,
  loopback для молчания до тайм-аута и закрытого порта; класс отказа и `checked_at`;
- `test_core_batch_probe.py` — `INVALID_CONFIG` с текстом, `REJECTED` с

  цел; `failed_profile_ids` с `ProbeResult`;
- тесты `ProfileEntry` — круговая сериализация, старый файл, неизвестная

- `test_ui_logic_profiles_view.py` — метки, подсказки с подставным `now`, сортировка;
- `test_core_failover.py` — отказавшие после непроверенных;
- строка сервера в GTK (`gtk`) и Qt (`qt`) — подсказка и признак ошибки.

## Не входит

- Разбор лога пробного ядра для конкретной причины (DNS, refused, TLS).
- Пометка устаревших результатов — понадобится автовыбору сервера.
- Причина отказа активного сервера по `health_probe`: это проверка рабочей
  сессии, а не замер.
- Отдельное действие повторной проверки: есть «Пинг» и пункт меню.
