# Замер задержки при активном TUN

Дата: 2026-11-07. Статус: дизайн, прошёл ревью по коду.

## Проблема

При подключении в режиме TUN замер задержки запрещён: `_can_probe` в `src/ui/controller.py` и
`make_batch_probe` в `src/ui/logic/latency.py` отказывают с тостом «Замер при активном TUN
недоступен». Пробное ядро (`src/core/batch_probe.py`) собирает outbound'ы без привязки к
интерфейсу, и его соединения уходят в туннель, то есть через текущий сервер. К задержке каждого
сервера прибавляется задержка текущего, а при мёртвом текущем все получают -1.

В состоянии «трафик заблокирован» (ядро упало под `tun_kill_switch`) замер формально разрешён,
но таблица `inet veblock` отбрасывает непомеченные сокеты пробного ядра: все серверы получают
-1 как раз тогда, когда пользователь ищет живой.

Маршруты на платформах разные:

| | Linux | Windows |
| --- | --- | --- |
| Маршрут в туннель | `ip route replace default dev xray0` (`core/scripts/tun_route_helper.sh`) | `0.0.0.0/1` и `128.0.0.0/1` на TUN (`src/winsvc/state.py`) |
| Физический маршрут по умолчанию | остаётся, только если у него была метрика | остаётся всегда |
| Обход туннеля рабочим ядром | `sockopt.interface`, `sockopt.mark`, маршрут `/32` до сервера | `sockopt.interface`, маршрут `/32` до сервера |
| `netbind.binding_confirmed` | честная проверка `ip route show default dev <if>` | всегда False, пока нет проверки на живой Windows |
| Блокировка трафика | таблица `inet veblock` пропускает только сокеты с `SOCKET_MARK` | нет |

На Linux привязка к интерфейсу сейчас работает в одних сетях и не работает в других. Если у
исходного маршрута не было метрики, помощник его заменяет, и сокету на `eth0` некуда идти. С тем
же связаны пропуски прямых проб диагностики (`SKIPPED(SYSTEM_RESTRICTED)`).

## Решения

| Вопрос | Решение |
| --- | --- |
| Путь пробы мимо туннеля | Привязка пробных outbound'ов к физическому интерфейсу, как у рабочего ядра |
| Маршруты Linux | Разбитый маршрут по умолчанию на TUN, как на Windows; физический не трогается |
| Блокировка трафика Linux | Пробные сокеты получают `SOCKET_MARK`; то же в состоянии «трафик заблокирован» |
| Имена серверов | DNS сети через прямой outbound пробного ядра, а не DNS туннеля |
| Когда замер под TUN не идёт | Только если физического интерфейса нет или `binding_confirmed` для него ложно |
| Без TUN и без блокировки | Пробный конфиг не меняется |

**Почему не маршрутизация по метке** (`ip rule fwmark` с отдельной таблицей, как в wg-quick).
Она надёжнее при смене IP сервера, но добавляет в журнал правило и таблицу и не помогает Windows.
Разбитый маршрут даёт одну логику на обеих платформах и чинит прямые пробы диагностики. К метке
можно вернуться отдельной задачей, если маршрута `/32` до сервера станет мало.

**Отклонено.** Маршруты `/32` до всех серверов: их сотни, а имена серверов меняют адреса.
Отдельное сетевое пространство: нужен root. Замер через рабочее ядро с вычитанием его задержки:
неточно и не работает при мёртвом текущем сервере. Добавление outbound'ов в рабочее ядро через
HandlerService: маршрутную задачу не решает.

## Пробное ядро

`probe_profiles` получает необязательную `ProbeRoute(interface, mark, dns_servers)`
(`src/core/batch_probe.py`). Её строит `probe_route(context)` из `src/ui/logic/latency.py`, и
вызывает её `batch_probe` в рабочем потоке замера, а не контроллер: на Windows поиск интерфейса —
снимок сети через PowerShell, в главном потоке он подвесил бы окно.

1. Сеанс не в TUN и трафик не заблокирован — `ProbeRoute` нет, конфиг прежний.
2. Иначе `iface = netbind.physical_interface(exclude=(tun_name,))`. Если интерфейса нет
   или `netbind.binding_confirmed(iface)` ложно — `ProbeUnavailable("Замер при активном TUN
   недоступен: нет маршрута мимо туннеля")`.
3. `mark = SOCKET_MARK` на Linux, на Windows не ставится. `dns_servers =
   system_dns_servers(iface)`.

`_can_probe` режим больше не проверяет. `make_batch_probe(context, on_unavailable)` при
`ProbeUnavailable` вызывает `on_unavailable(text)` и пробрасывает ошибку: контроллер показывает
текст тостом через `loop.dispatch`, `LatencyRunner` отдаёт всем профилям -1 и
`last_run_complete = False`, поэтому «Оставить рабочие» ничего не удаляет. Отказ случается, когда
физической сети нет или помощник старый: -1 здесь правда, а не заглушка.

С `ProbeRoute` пробный конфиг меняется так:

- у каждого `proxy-N`, кроме серверов на loopback, — `sockopt.interface`; у всех — `sockopt.mark`
  (если задана) и `domainStrategy: UseIPv4`, если адрес сервера — имя. Функции привязки, метки и
  разрешения имени выносятся из `src/core/config_builder.py` в `src/core/sockopt.py`
  (`bind_to_interface`, `mark_socket`, `resolve_in_core`); рабочий билдер вызывает их же;
- outbound `direct` (freedom) с той же привязкой и меткой;
- блок `dns` с `dns_servers`, `queryStrategy: UseIPv4` и тегом; правило `inboundTag: [<тег>]
  -> direct`. Без него запросы DNS-модуля ушли бы в первый outbound, то есть в `proxy-1`. Если
  DNS сети не найден, блока нет, и имена разрешает система, то есть туннель. Это хуже, но
  честно: задержка меряется по HTTP-запросу, а не по разрешению имени.

Пробное ядро запускается тем же бинарником, что и рабочее. На Linux у него `cap_net_admin` из
postinst, без этой возможности TUN бы не поднялся, поэтому `SO_MARK` доступен.

## Маршруты Linux

Помощник получает новое действие и новую семантику `apply`; старые действия остаются ради журнала
старой версии:

```sh
# apply <tun> <proxy_ip> <gw|-> <dev> <metric|->  (аргументы прежние, метрика не используется)
ip route replace "$proxy_ip/32" [via "$gateway"] dev "$dev"
ip route replace 0.0.0.0/1 dev "$tun_name"
ip route replace 128.0.0.0/1 dev "$tun_name"

# release <tun> <proxy_ip>
ip route del 0.0.0.0/1 dev "$tun_name"    || true
ip route del 128.0.0.0/1 dev "$tun_name"  || true
ip route del "$proxy_ip/32"               || true
```

`restore` не меняется: он возвращает заменённый маршрут по умолчанию после сеанса старой версии.
Вызывать его в новой схеме нельзя: после смены сети в сеансе `ip route replace default via
<старый шлюз>` подменил бы живой маршрут NetworkManager. `features` печатает ещё `split`.

`src/sys/linux/tun_route.py`:

- `apply_tun_routes` спрашивает `features` помощника (функция `_helper_features` переезжает из
  `src/sys/linux/tun_access.py`). Со `split` в журнал пишется `{"op": "route.release",
  "tun_name", "proxy_ip"}`, без него — прежняя запись `route.restore` и прежнее поведение.
  Запасной путь без помощника (`_run_ip_batch_privileged`) ставит разбитый маршрут и пишет
  `route.release`;
- `restore_tun_routes` по `op` записи зовёт `release` или `restore`; `TunRouteState` получает
  поле `split`;
- `recover_tun_routes` для `route.release` зовёт `release` без проверки маршрута по умолчанию:
  TUN упавшего сеанса исчез вместе со своими маршрутами, остаётся убрать `/32`, а удаление
  отсутствующего маршрута безвредно. Для `route.restore` логика прежняя;
- `_valid_entry` принимает обе записи;
- комментарий о метрике в начале модуля и раздел о падении ядра в
  `docs/plans/2026-11-03-tun-kill-switch-design.md`: маршруты в TUN исчезают вместе с
  интерфейсом, утечку закрывает только блокировка трафика. Так уже было при маршруте с
  метрикой, теперь — всегда.

`netbind.active_tunnel_interface` на Linux ищет TUN в `ip route show 0.0.0.0/1`, а не только
в `default`. `get_default_interface` в `src/sys/linux/vpn.py` не меняется: TUN она и так
пропускает.

**rp_filter.** Ответ сервера приходит на `eth0`, а лучший маршрут к серверу ведёт в TUN через
`0.0.0.0/1`. Строгий `rp_filter` (1) такой пакет отбрасывает, и все пробы получают -1; свободный
(2) пропускает. Ubuntu и systemd ставят 2 по умолчанию. `binding_confirmed` на Linux
дополнительно читает `/proc/sys/net/ipv4/conf/{all,<if>}/rp_filter` и при значении 1 у любого
из них отказывает: это одна проверка на пробу и на прямые пробы диагностики. Снимать строгий
режим помощником — отдельная задача, если понадобится.

Риск: программа, которая сама привяжется к физическому интерфейсу, обойдёт туннель. С уровнем
`full` её закрывает таблица `inet veblock`, с `ipv6_only` — нет. Так же уже сейчас в сетях, где у
маршрута по умолчанию есть метрика. Чужой VPN с теми же маршрутами `/1` (OpenVPN `def1`)
`ip route replace` перепишет на TUN; сейчас в такой сети TUN проигрывает ему.

## Windows

Маршруты не меняются. Нужно:

- `netbind.binding_confirmed` — `netinfo.default_route(snapshot)` указывает на этот адаптер,
  вместо постоянного False. Это включит и прямые пробы диагностики, поэтому проверку на живой
  Windows нужно пройти для обоих;
- `netbind.active_tunnel_interface` сейчас слеп: снимок `netinfo` собирает только маршруты
  `0.0.0.0/0`, а у TUN их нет. Снимок получает и `0.0.0.0/1`; `default_route` по-прежнему
  смотрит только на `/0`;
- NRPT шлёт все имена в DNS туннеля, поэтому блок `dns` пробного ядра для Windows обязателен:
  адреса — `system_dns_servers(iface)` из `src/sys/windows/resolver.py`. Запросы к ним уходят
  через `direct` с `IP_UNICAST_IF` и NRPT не проходят.

## Ошибки

- Физический интерфейс исчез во время замера — соединения пробного ядра падают, профили получают
  -1. `failed_profile_ids` не удаляет серверы, если не ответил ни один; частичный отказ ничем не
  отличается от обрыва сети без TUN.
- Ядро отвергает `sockopt.interface` — профиль отсеивается `split_accepted` и получает -1. Это
  ловят тесты конфига, а не пользователь.
- Блокировка трафика `full` без метки на пробе — все -1. Тест проверяет, что метка есть.
- Старый помощник (без `split`) с новым приложением — маршрут по умолчанию заменяется, как раньше;
  в сети без метрики замер под TUN даёт тост и -1.
