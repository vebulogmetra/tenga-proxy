# Замер задержки при активном TUN

Дата: 2026-11-07. Статус: дизайн.

## Проблема

При подключении в режиме TUN замер задержки запрещён: `_can_probe` в `src/ui/controller.py` и
`make_batch_probe` в `src/ui/logic/latency.py` отказывают с тостом «Замер при активном TUN
недоступен». Пробное ядро (`src/core/batch_probe.py`) собирает outbound'ы без привязки к
интерфейсу, и его соединения уходят в туннель, то есть через текущий сервер. К задержке каждого
сервера прибавляется задержка текущего, а при мёртвом текущем все получают -1.

Маршруты на платформах разные:

| | Linux | Windows |
| --- | --- | --- |
| Маршрут в туннель | `ip route replace default dev xray0` (`core/scripts/tun_route_helper.sh`) | `0.0.0.0/1` и `128.0.0.0/1` на TUN (`src/winsvc/state.py`) |
| Физический маршрут по умолчанию | остаётся, только если у него была метрика | остаётся всегда |
| Обход туннеля рабочим ядром | `sockopt.interface`, `sockopt.mark`, маршрут `/32` до сервера | `sockopt.interface`, маршрут `/32` до сервера |
| `netbind.binding_confirmed` | честная проверка `ip route show default dev <if>` | всегда False, пока нет проверки на живой Windows |
| Блокировка трафика | таблица `inet veblock` пропускает только сокеты с `SOCKET_MARK` | нет |

На Linux привязка к интерфейсу сейчас работает в одних сетях и не работает в других. Если у
исходного маршрута не было метрики, помощник его заменяет, и сокету на `eth0` некуда идти. С тем
же связаны пропуски прямых проб диагностики (`SKIPPED(SYSTEM_RESTRICTED)`).

## Решения

| Вопрос | Решение |
| --- | --- |
| Путь пробы мимо туннеля | Привязка пробных outbound'ов к физическому интерфейсу, как у рабочего ядра |
| Маршруты Linux | Разбитый маршрут по умолчанию на TUN, как на Windows; физический не трогается |
| Блокировка трафика Linux | Пробные сокеты получают `SOCKET_MARK` |
| Имена серверов | DNS сети через прямой outbound пробного ядра, а не DNS туннеля |
| Когда замер под TUN запрещён | Только если `binding_confirmed` для физического интерфейса ложно |
| Без TUN | Пробный конфиг не меняется |

**Почему не маршрутизация по метке** (`ip rule fwmark` с отдельной таблицей, как в wg-quick).
Она надёжнее при смене IP сервера, но добавляет в журнал правило и таблицу, требует
`src_valid_mark` или connmark при строгом `rp_filter` и не помогает Windows. Разбитый маршрут
даёт одну логику на обеих платформах и чинит прямые пробы диагностики. К метке можно вернуться
отдельной задачей, если маршрута `/32` до сервера станет мало.

**Отклонено.** Маршруты `/32` до всех серверов: их сотни, а имена серверов меняют адреса.
Отдельное сетевое пространство: нужен root. Замер через рабочее ядро с вычитанием его задержки:
неточно и не работает при мёртвом текущем сервере. Добавление outbound'ов в рабочее ядро через
HandlerService: маршрутную задачу не решает.

## Пробное ядро

`probe_profiles` получает необязательную `ProbeRoute(interface, mark, dns_servers)`. Её строит
`make_batch_probe` из контекста в момент замера:

1. Сеанс не в TUN — `ProbeRoute` нет, конфиг прежний.
2. Сеанс в TUN — `iface = netbind.physical_interface(exclude=(tun_name,))`. Если интерфейса нет
   или `netbind.binding_confirmed(iface)` ложно — `RuntimeError`, как сейчас, и тот же тост.
3. `mark = SOCKET_MARK` на Linux, на Windows не ставится. `dns_servers =
   system_dns_servers(iface)`.

С `ProbeRoute` пробный конфиг меняется так:

- у каждого `proxy-N`, кроме серверов на loopback, — `sockopt.interface`, `sockopt.mark` и
  `domainStrategy: UseIPv4`, если адрес сервера — имя. Привязку и метку ставят те же функции, что
  у рабочего конфига (`_bind_to_interface`, `_prepare_tun_sockets` из `src/core/config_builder.py`):
  их нужно вынести в общий модуль, а не копировать;
- outbound `direct` (freedom) с той же привязкой и меткой;
- блок `dns` с `dns_servers` и тегом, правило `inboundTag: [<тег dns>] -> direct`. Если DNS сети
  не найден, блока нет, и имена разрешает система, то есть туннель. Это хуже, но честно: задержка
  меряется по HTTP-запросу, а не по разрешению имени.

Пробное ядро запускается тем же бинарником, что и рабочее. На Linux у него `cap_net_admin` из
postinst, без этой возможности TUN бы не поднялся, поэтому `SO_MARK` доступен.

`_can_probe` перестаёт проверять режим сам: он спрашивает ту же функцию, что `make_batch_probe`
(`probe_route(context)`), и показывает тост, только если она отказала. Текст тоста: «Замер при
активном TUN недоступен: нет маршрута мимо туннеля».

## Маршруты Linux

`apply` помощника:

```sh
ip route replace "$proxy_ip/32" [via "$gateway"] dev "$dev"
ip route replace 0.0.0.0/1 dev "$tun_name"
ip route replace 128.0.0.0/1 dev "$tun_name"
```

`restore`: удалить `0.0.0.0/1` и `128.0.0.0/1`, если они на TUN, и `/32`. Возврат маршрута по
умолчанию остаётся как есть: при новых маршрутах он ничего не меняет, а после сеанса старой версии
возвращает заменённый. Аргументы и журнал прежние, поэтому записи упавшего сеанса старой версии
откатываются новой без миграции.

Что поменять вместе с помощником:

- запасной путь без помощника в `apply_tun_routes` и `restore_tun_routes` — те же команды;
- `recover_tun_routes` — признаком оставшегося сеанса становятся и маршруты `0/1`, `128/1` на TUN.
  Если TUN исчез, они исчезли вместе с ним, и остаётся убрать `/32`;
- `netbind.active_tunnel_interface` на Linux — искать TUN и в `ip route show 0.0.0.0/1`;
  на Windows сверить, что выбор по наименьшей метрике видит разбитый маршрут;
- комментарий о метрике в `src/sys/linux/tun_route.py` и раздел о падении ядра в
  `docs/plans/2026-11-03-tun-kill-switch-design.md`: после падения ядра маршруты в TUN исчезают
  вместе с интерфейсом, утечку закрывает только блокировка трафика. Так уже было при маршруте с
  метрикой, теперь — всегда;
- `tests/vm/guest/lab.py` и проверки, которые читают `ip route show default`.

Риск: программа, которая сама привяжется к физическому интерфейсу, обойдёт туннель. С уровнем
`full` её закрывает таблица `inet veblock`, с `ipv6_only` — нет. Так же уже сейчас в сетях, где у
маршрута по умолчанию есть метрика.

## Windows

Маршруты не меняются. Нужно:

- `netbind.binding_confirmed` на Windows — проверять, что у адаптера есть свой маршрут
  `0.0.0.0/0` в снимке `netinfo`, вместо постоянного False. Это включит и прямые пробы
  диагностики, поэтому проверку на живой Windows нужно пройти для обоих;
- NRPT шлёт все имена в DNS туннеля, поэтому блок `dns` пробного ядра для Windows обязателен:
  адреса — `system_dns_servers(iface)` из `src/sys/windows/resolver.py`. Запросы к ним уходят
  через `direct` с `IP_UNICAST_IF` и NRPT не проходят.

## Ошибки

- Физический интерфейс исчез во время замера — соединения пробного ядра падают, профили получают
  -1. `failed_profile_ids` уже не удаляет серверы при неполном замере или без сети; дополнительно
  «Оставить рабочие» отменяется, если до и после замера физический интерфейс разный.
- Ядро отвергает `sockopt.interface` — профиль отсеивается `split_accepted` и получает -1. Это
  ловят тесты конфига, а не пользователь.
- Блокировка трафика `full` без метки на пробе — все -1. Тест проверяет, что метка есть.
