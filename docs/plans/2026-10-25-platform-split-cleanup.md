# Разделение Linux и Windows — план исправлений

> **For Claude:** это дорожная карта, а не исполняемый план. Пошаговый план
> пишется на каждую фазу отдельно, первой задачей — сверка с кодом: строки
> сдвинутся, привязываться нужно к содержимому.

**База:** desktop 0.17.1 (`ad4d0c7`), 2026-10-25.

## Исходное состояние

Обе платформы — одно дерево `src/`, признак ОС один: `IS_WINDOWS` в
`src/core/platform_info.py`.

- `src/sys/{proxy,vpn,tun_route,tun_dns,resolver,single_instance}.py` —
  фасады, выбирают `src/sys/linux/*` или `src/sys/windows/*` **при импорте**.
- `src/core/` — точечные развилки: пути (`config.py`), Stats API
  (`stats_endpoint.py`), проверка после DNS (`health_probe.py`), ассет
  обновления (`app_update.py`), `WindowsXrayManager` (`context.py`).
- TUN на Windows — служба `TengaProxySvc` (`src/winsvc/`): политика конфига,
  журнал изменений сети, откат при остановке, падении и старте.
- TUN на Linux — `setcap` на xray при установке AppImage, маршруты из GUI
  через `ip` / `sudo -n ip` / `sudo -n tun-route-helper`. Состояние маршрутов
  (`ConnectionService._tun_route_state`) живёт только в памяти.
- UI — около 15 проверок `IS_WINDOWS` в страницах, диалогах и окне; трей и
  стили уже разведены по модулям.
- CI — только `windows.yml` и `docs.yml`. Linux не проверяется.

## Проблемы

| # | Проблема | Последствие |
|---|---|---|
| P1 | Нет CI для Linux | Регрессии основной платформы видны только на машине разработчика; Windows-правки (как в 0.17.1) приходят без прогона Linux |
| P2 | Контракт фасадов не зафиксирован | Сигнатуры `linux/*` и `windows/*` могут разойтись незаметно — ошибка всплывёт только на другой ОС |
| P3 | Фасады выбирают реализацию при импорте, хотя `platform_info.py` обещает чтение «в момент вызова» | Подмена `IS_WINDOWS` в тестах на фасады не действует; документация врёт |
| P4 | Linux TUN не переживает падение GUI | Маршруты и DNS остаются в системе, сеть сломана до ручного `ip route` |
| P5 | Привилегии Linux TUN: `setcap` + `sudo -n` | Работает только при беспарольном sudo или установленном помощнике; поведение неочевидно, ошибка — молчаливый откат на `ip` без прав |
| P6 | UI-развилки рассыпаны по виджетам | Каждая новая разница платформ — ещё один `if` в странице; тексты не собраны в одном месте |

## Фазы

Порядок — от дешёвого и страхующего к дорогому. Фазы 1–3 независимы от
решения по фазе 4.

### Фаза 1. Linux CI (P1)

- `.github/workflows/linux.yml` на `ubuntu-latest`: `uv sync --extra dev`,
  `python cli.py lint-all`, `uv run pytest`.
- Отдельная задача: `make test-gtk` под `xvfb-run` + `dbus-run-session` и
  `make test-tray` — если пакеты GTK4/libadwaita 1.5 есть в образе runner'а;
  если нет, записать это в статус и оставить только unit-тесты.
- Опционально: сборка AppImage как артефакт на тег `v*`, по аналогии с
  установщиком Windows.

**Итог:** каждый push в `develop` проверяется на обеих ОС.

### Фаза 2. Контракт платформы (P2, P3)

- Тест паритета: для каждого фасада `linux` и `windows` экспортируют одни и
  те же имена с совместимыми сигнатурами (`inspect.signature`, без учёта
  keyword-only аргументов для внедрения зависимостей вроде
  `registry=`/`notify=`). Падает при расхождении — на любой ОС.
- Решить семантику выбора и привести к одной:
  - **вариант А (рекомендуется):** оставить выбор при импорте, исправить
    docstring `platform_info.py` — «фасады `src/sys/` выбирают реализацию
    при импорте, остальной код читает флаг при вызове». Минимум изменений;
    тест паритета закрывает главный риск.
  - вариант Б: ленивые функции-прокладки в фасадах. Больше кода, выигрыш
    только в тестах.
- Убрать реэкспорт `src/sys/__init__.py`, если у него нет потребителей кроме
  `connection.py` (проверить).

**Итог:** расхождение реализаций ловится тестом, документация совпадает с кодом.

### Фаза 3. Откат TUN на Linux (P4)

Повторить модель службы Windows без самой службы:

- Вынести `Journal` из `src/winsvc/journal.py` в общий модуль
  (например `src/core/net_journal.py`); `winsvc` импортирует оттуда.
- `src/sys/linux/tun_route.py` и `tun_dns.py` записывают каждое изменение
  (маршрут, метрика, DNS-ссылка) в журнал в `CORE_DIR` до применения и
  удаляют запись после успешного отката.
- При старте приложения (до подключения) — откат незакрытого журнала.
  Права: те же пути, что и при применении (`sudo -n` / помощник).
- Тесты — на внедрённом исполнителе команд, без настоящего `ip`.
  **Не запускать xray с TUN на машине разработчика** — проверка на VM.

**Итог:** падение GUI не оставляет систему без сети; после перезапуска всё
возвращается.

### Фаза 4. Привилегии Linux TUN (P5) — нужен дизайн

Требует отдельного решения владельца проекта, варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Оставить `setcap` + помощник через `sudo -n`, но явно сообщать в UI, чего не хватает | Минимум работы | Остаётся зависимость от sudoers |
| Помощник через polkit (`pkexec` + `.policy`) | Стандарт для десктопа, один запрос пароля | Ещё один установочный артефакт; в AppImage polkit-политику нужно ставить в систему |
| systemd-служба по модели `TengaProxySvc` (сокет, политика, журнал) | Симметрия с Windows, переиспользуется `policy.py`/`journal.py` | Самый дорогой; требует root при установке, усложняет AppImage |

Рекомендация: начать с первого варианта (диагностика в UI), второй — если
пользователи упираются в sudo. Третий — только если появится потребность
запускать xray от root на Linux.

### Фаза 5. Развилки UI (P6)

- Тексты: все строки, зависящие от ОС (заголовки разделов настроек,
  подписи страниц подписок и мониторинга), — в `src/ui/logic/platform_texts.py`,
  в виджетах — вызов функции, а не `if`.
- Отступы и размеры — в `style-windows.css`, а не в коде, где это возможно
  (сверить с правками 0.17.1 в `window.py`, `dialogs/base.py`, `name_label.py`).
- Оставшиеся `IS_WINDOWS` в `src/ui/` — только там, где меняется поведение
  (флаги GApplication, сигналы, трей, активация). Тест-«сторож»: перечень
  допустимых файлов с `IS_WINDOWS` в `src/ui/`.

**Итог:** новая разница платформ в UI добавляется в одно место.

### Фаза 6. Документация

- `CLAUDE.md`, `AGENTS.md`: раздел о разделении платформ — фасады, контракт,
  журнал на обеих ОС, Linux CI.
- `docs/{ru,en}/development.md`: как проверять изменения под обе ОС.

## Общие правила

- TDD, один логический коммит на задачу, сообщения на русском в стиле
  репозитория. Рефакторинг и изменение поведения — разными коммитами.
- Перед коммитом — `uv run pytest` и `python cli.py lint-all`.
- Поведение Windows не меняется, кроме переноса `Journal` (фаза 3) — там
  прогон CI `windows.yml` обязателен.
- Что не удалось проверить, записывается в «Статус», а не замалчивается.
