# Блокировка трафика при обрыве: режим TUN на Linux и IPv6

Дата: 2026-11-03. Статус: дизайн согласован, реализация не начата.

## Проблема

Механизма блокировки при обрыве нет. Поле `vpn_strict_route` в `src/db/data_store.py`
нигде не используется.

- **Падение xray в TUN.** `ip route replace default dev xray0` добавляет маршрут с метрикой 0,
  а исходный маршрут с метрикой остаётся. Интерфейс исчезает вместе со своим маршрутом, и
  трафик уходит по следующему. Комментарий в `src/sys/linux/tun_route.py:20` описывает только
  случай исходного маршрута без метрики.
- **Смена сервера.** `connect()` начинает с `disconnect()`, и между старым и новым ядром
  маршруты возвращаются к исходным.
- **IPv6.** В TUN заворачивается только IPv4. В сети с IPv6 приложения ходят мимо прокси
  постоянно, даже без обрыва.
- **Падение ядра не обрабатывается.** Автопереключение выходит на `server_probed=False`,
  перезапуска нет, а `is_running` сбрасывает только отключение.

Если сервер молчит, а xray жив, трафик напрямую не идёт: он остаётся в ядре. Исключение —
то, что идёт напрямую по правилам маршрутизации.

## Решения

| Вопрос | Решение |
| --- | --- |
| Срок блокировки | От подключения до «Отключить», выхода через меню или перезагрузки |
| Падение ядра, падение приложения, смена сервера | Блокировка остаётся |
| VPN | Поддерживается с первой версии |
| IPv6 в TUN | Блокируется всегда, кроме локальной сети, даже с выключенной настройкой |
| Механизм | Своя таблица `nftables` |

**Почему не blackhole.** Прямой и серверный outbound привязаны к физическому интерфейсу
(`src/core/config_builder.py:337`). Насколько известно из логики ядра Linux, привязанный сокет
тоже упрётся в blackhole, и `direct` сломается. Проверить это не удалось: AppArmor запрещает
непривилегированные user namespaces. Отдельная таблица маршрутов с `ip rule` решает это, но
её обходят более точные маршруты чужих VPN, а шлюз в ней устаревает при смене сети.

## Архитектура

- **`src/sys/linux/tun_firewall.py`** собирает описание политики и применяет его через
  помощника. Уровни: `ipv6_only` и `full`.
- **`src/sys/tun_firewall.py`** — фасад. На Windows реализация пока ничего не делает; совпадение
  имён проверяет `tests/test_sys_facades.py`.
- **`tun-route-helper`** получает действия `firewall-apply` и `firewall-remove`. Помощник
  запускается от root без пароля, поэтому готовых правил не принимает: он проверяет аргументы
  и сам подставляет их в шаблон.
- **`ConnectionService`** управляет блокировкой. CLI работает без него и в первую версию не
  входит.
- **`sockopt.mark`** ставится на все outbound ядра в TUN при любой настройке. Поставить такую
  метку может только процесс с `cap_net_admin`, поэтому обычное приложение её не подделает.

## Жизненный цикл

| Событие | Блокировка |
| --- | --- |
| Подключение | Ставится до запуска xray |
| Смена сервера вручную или автоматически | Остаётся; маршруты можно откатывать и ставить заново |
| Падение xray | Остаётся; приложение показывает «Трафик заблокирован» |
| «Отключить» или выход через меню | Снимается после остановки ядра |
| Падение приложения | Остаётся до следующего запуска; `recover_network()` снимает её и сообщает об этом |
| Перезагрузка | Таблица живёт в памяти и исчезает |
| Удаление пакета | Снимает `prerm` |

`connect()` больше не вызывает публичный `disconnect()`: он делится на внутренний
`_teardown(keep_block=True)` и публичный `disconnect()`, который снимает блокировку.

Ошибки:

- **Первое подключение не удалось:** блокировка снимается, ошибка показывается как сейчас.
- **Смена сервера не удалась:** блокировка остаётся, снять её можно кнопкой.
- **Блокировку не удалось поставить:** при `full` подключение отменяется с объяснением, при
  `ipv6_only` продолжается с предупреждением.

## Правила

Уровень `full`:

```
table inet veblock {
  chain output {
    type filter hook output priority 0; policy accept;
    oif lo accept
    meta mark 0x7E6A accept              # сокеты xray
    oifname "xray0" accept
    oifname "tun0" accept                # если есть VPN
    ip daddr <адрес VPN-сервера> accept  # если есть VPN
    meta l4proto { tcp, udp } th dport 53 drop   # только без открытого окна DNS
    udp sport 68 udp dport 67 accept     # DHCP
    icmpv6 type { nd-router-solicit, nd-neighbor-solicit, nd-neighbor-advert } accept
    ip daddr { локальные сети, 224.0.0.0/4, 255.255.255.255 } accept
    ip6 daddr { fc00::/7, fe80::/10, ff00::/8 } accept
    drop
  }
  chain forward { ... }   # те же разрешения, кроме метки и DHCP
}
```

Уровень `ipv6_only` отличается так: нет правила DNS, последняя строка —
`meta nfproto ipv6 drop`. IPv4 не затрагивается.

### VPN

Интерфейс берётся из `get_vpn_interface()`. Поля `VPN.GATEWAY` у `nmcli` нет. Адрес берётся из
`vpn.data`: ключ `remote` у OpenVPN (проверено на подключении NetworkManager), ключ `gateway`
у других плагинов (предположение, проверить). Значение может быть именем хоста или списком,
поэтому оно разрешается в адреса. Запасной источник — маршруты `/32` через физический
интерфейс. Если адрес не найден, при `full` подключение отменяется.

Блокировка применяется после подъёма VPN, потому что от него зависят аргументы правил.

### DNS

После падения ядра resolved вернётся к DNS физического интерфейса: обычно это роутер, то есть
локальная сеть, и без отдельного правила запросы утекут. Полный запрет ломает подключение:
`apply_tun_routes` и, возможно, сам xray разрешают адрес сервера через систему. Поэтому:

1. **На время `connect()`** порт 53 в локальную сеть открыт.
2. **После успешного `route_system_dns_to_tun`** таблица применяется заново, уже с запретом.

Цена: несколько секунд подключения DNS-запросы могут уходить на роутер. Трафик при этом закрыт.
Если направить DNS в TUN не удалось, например на системе без resolved, запрет не ставится, иначе
DNS перестанет работать совсем. Приложение предупреждает об этом.

### Прочее

- **Docker и виртуальные машины:** локальные сети разрешены, выход в интернет только через TUN
  или VPN. `drop` в любой базовой цепочке окончателен, поэтому наш `accept` не отменяет правил
  Docker.
- **Локальная сеть** открыта всегда.
- **Открытые соединения:** правила `ct state established` нет, поэтому соединения мимо туннеля,
  открытые до подключения, обрываются. Ответы на входящие подключения из локальной сети проходят.
- **Captive portal:** страница входа при блокировке не откроется, сначала нужно отключиться.

## Интерфейс

**Настройка.** `tun_kill_switch: bool = False` в `DataStore`. В группе «Режим работы» строка
«Блокировать трафик при обрыве» с подсказкой «Если соединение прервётся, трафик не пойдёт
напрямую. Локальная сеть останется доступной». В GTK — `Adw.SwitchRow`, в Qt — `QCheckBox`.

- Активна только в режиме TUN. На Windows скрыта: условие показа лежит в `src/ui/logic/`.
- Входит в `runtime_snapshot`, поэтому изменение показывает обычный баннер о переподключении.
- `tun_problems()` дополнительно сообщает об отсутствии `nft` и о старом помощнике.

**Новое состояние** в `src/ui/logic/status.py` и таблице
`docs/plans/2026-11-02-shared-ui-design.md`:

| Заголовок | Подпись | Действие логотипа | Логотип |
| --- | --- | --- | --- |
| «Трафик заблокирован» | последний сервер | «Переподключить» | предупреждение |

Под карточкой баннер «Соединение потеряно. Трафик закрыт, локальная сеть доступна» с кнопкой
«Снять блокировку». В трее оба действия и значок ошибки. Логотип ведёт к переподключению, чтобы
случайный клик не открывал трафик. Снятие работает как «Отключить», без подтверждения.

**Запуск после падения приложения.** `recover_network()` сообщает о снятой блокировке, контроллер
показывает «Прошлый сеанс завершился сбоем, блокировка трафика снята».

## Падение ядра

Работает и без настройки: это исправление отдельной ошибки.

1. **Обнаружение.** `XrayManager` получает колбэк `on_unexpected_exit`, который вызывает поток
   чтения вывода при закрытии pipe. Монитор не подходит: он зависит от настройки мониторинга и
   срабатывает раз в 10 секунд. Устройство потока уточнить при составлении плана.
2. **Очистка.** `ConnectionService.handle_core_exit()` возвращает маршруты и сбрасывает состояние,
   блокировку и VPN не трогает.
3. **Перезапуск.** Одна автоматическая попытка к тому же серверу. Если ядро уже падало за последнюю
   минуту, попытки нет.
4. **Если не вышло.** С настройкой — «Трафик заблокирован» и `notify_user`. Без неё — «Ошибка» с
   текстом «Ядро остановилось, трафик идёт напрямую».

## Что проверить в первую очередь

Проводить в виртуалке или отдельном сетевом пространстве: таблица `inet veblock` общая на систему,
и запуск на машине разработчика заденет рабочий сеанс.

1. **`sockopt.mark` вместе с `sockopt.interface`:** метка должна доходить до `nftables` на всех
   outbound, включая DNS. Если нет, выбор механизма пересматривается. `skuid` не подходит: xray
   работает от имени пользователя, как и остальные приложения.
2. **Как xray разрешает адрес сервера:** попадают ли его DNS-запросы под метку. От этого зависит,
   нужно ли окно DNS самому ядру или только `apply_tun_routes`.

Ручная проверка на установленном deb в виртуалке:

- `kill -9` для xray и для приложения: внешний адрес недоступен, локальная сеть доступна.
- Смена сервера, смена Wi-Fi, проверка утечек IPv6 и DNS.
- OpenVPN через NetworkManager, включая обрыв и переподключение при активной блокировке.
- Контейнер Docker, удаление пакета.

## Порядок работ

Каждый этап можно выпустить отдельно.

1. **Обработка падения ядра** и правка комментария в `src/sys/linux/tun_route.py`.
2. **Эксперименты** из раздела выше.
3. **Основа и IPv6:** помощник, фасад, метка, `ipv6_only`, `nftables` в `Depends`, очистка в
   `prerm`, комментарий в `sudoers`.
4. **Уровень `full`:** жизненный цикл, окно DNS, VPN.
5. **Интерфейс GTK и Qt,** таблица состояний в общем дизайне, `CLAUDE.md`, документация.

## Вне этапа

Windows, режим системного прокси, CLI, проксирование IPv6.

На Windows при следующем этапе блокировать придётся файрволом или WFP из службы: откат маршрутов
при падении ядра (`src/winsvc/state.py:180`) и создаёт утечку. Режим системного прокси полностью
не защитить: приложения, которые его игнорируют, ходят мимо xray.

## Что заметит пользователь

Блокировка IPv6 включается у всех в TUN без настройки. Сайты только с IPv6 перестанут открываться:
это нужно упомянуть в примечаниях к выпуску.
