# Перенос актуальных возможностей Android на десктоп — план реализации

> **Для исполнителя:** использовать навык `superpowers:executing-plans`, выполнять задачи последовательно с проверкой результатов каждого этапа.

**Цель:** перенести применимые улучшения Android 1.2.12–1.4.5 в Linux-клиент, начиная с защиты конфигурации и заканчивая настройками и обслуживанием приложения.

**Архитектура:** сохраняем Python, GTK4/libadwaita и отдельный процесс xray. Политику безопасности и решения о применении настроек выносим в GTK-независимые модули. Рабочее подключение, замер и импорт используют общие правила построения конфигурации.

**Стек:** Python 3.11+, requests, GTK4, libadwaita, pytest, Ruff, xray-core 26.9.9.

**Статус:** код задач 1–14 реализован в текущем рабочем дереве; проверки и ограничения зафиксированы ниже. Задача 15 остаётся условной и не запускается без инфраструктуры подписи релизов. База: desktop `a17384a` (0.16.2), Android `8b056d4d` (1.4.5), 20.10.2026. Пути Android ниже относительны соседнему `../tenga-proxy-android/`.

Уточнения реализации:

- `downloadSettings`, realm, xdns и xicmp из чужих транспортных параметров отбрасываются:
  они меняют назначение соединения. Остальные поддержанные вложенные структуры
  проверяются по полям, а не копируются целиком.
- Импорт общей маршрутизации сохраняет списки в атомарном settings.json и включает
  `routing.use_saved_lists`. Это не даёт старым текстовым файлам подменить подтверждённый
  импорт при следующем подключении. У старых установок флаг выключен и файловые списки
  продолжают работать.
- Сборка соединения использует копии настроек и профиля: автосохранение во время запуска
  не может незаметно подменить снимок реально выбранных параметров.
- Дополнительный DNS не назван строгим failover. Последовательность реальных запросов
  при отказе первого resolver отдельно не гарантируется.
- Xbox DNS не перенесён: [официальный сайт](https://xbox-dns.ru/) сообщает о временной
  недоступности и адресах, отличающихся от Android; источники Quad9/Comss приведены в
  `docs/ru/routing.md`.
- Подпись геобаз не заявляется: SHA256 и зафиксированный релиз обеспечивают описанную
  целостность и контроль версий, а не независимую аутентификацию издателя.

## Границы и выбранный подход

Рассмотрены три подхода: буквальный перенос Android, выбор отдельных исправлений и поэтапное сближение с учётом Linux. Выбран третий: буквальный перенос ломает существующие split-DNS и NetworkManager, а только исправления безопасности оставляют проблемы применения настроек.

VK-туннель вынесен в `2026-10-20-vk-tunnel-linux.md`. Android-специфичные metered state, разрешения уведомлений, Keystore и жизненный цикл VpnService не копируются. Переименование десктопа в Veblock не входит в план: совместимость ссылок отделена от брендинга.

Уже сделанное не реализуем заново: пакетный пинг, failover, метаданные и загрузка подписок через прокси, общая фрагментация, выбор темы, ротация журналов, проверка обновлений ядра, поставка геобаз. Десктопное хранение логов три дня сохраняется; Android-срок семь дней не даёт самостоятельной пользы.

## Общие правила выполнения

1. До кода сверить текущую ветку, `AGENTS.md`, связанные тесты и изменения после указанной базы. Не перезаписывать чужие изменения.
2. Каждую поведенческую задачу выполнять циклом: добавить регрессионный тест → запустить и увидеть ожидаемое падение → реализовать минимум → запустить целевые тесты → отдельный логический коммит. Рефакторинг выделять отдельно.
3. Новые настройки имеют безопасные значения по умолчанию и тест чтения старого JSON. Проверять CLI и GUI, а не только форму ввода.
4. Конфиги проверять настоящим `xray -test` через существующий `tests/test_fmt_xray_config_valid.py`. Использовать только loopback SOCKS/HTTP-inbound, не создавать тестовый TUN и не менять DNS рабочей системы.
5. Все примеры синтетические, без настоящих подписок и ключей. Изменения UI проверять в изолированном окне; сохранять снимки в `docs/screenshots/`.
6. Указанные ниже новые файлы — предлагаемое размещение. Перед созданием проверить, нет ли уже подходящей реализации. Точное число тестов заранее не фиксируется; ожидается отсутствие новых падений и необъяснённых пропусков.

### Задача 2. Единая политика URL подписок и редиректов

**Создать:** `src/sub/url_policy.py`, `tests/test_sub_url_policy.py`.
**Изменить:** `src/sub/updater.py`, `src/sub/url_change.py`, `src/ui/logic/forms.py`, `src/db/config.py`, `src/ui/dialogs/settings.py`.

1. Добавить тесты HTTPS, неверных портов, userinfo, fragment, localhost, private/link-local/loopback/multicast/unspecified IPv4/IPv6, IPv4-mapped IPv6, короткой/числовой/восьмеричной записи IPv4 и цепочек редиректов.
2. По умолчанию разрешать публичный HTTPS. HTTP и локальные подписки поддерживать только явным исключением пользователя для конкретного источника; существующие записи сохранять, но запрос приостанавливать с объяснением и возможностью разрешения.
3. Проверять URL до первого запроса и каждый `Location`, запретить автоматическое следование редиректам, downgrade и бесконечные цепочки. Обрабатывать относительный Location. Исключение одного источника не разрешает произвольный переход в LAN; чувствительные заголовки не переносить на другой origin без отдельной политики.
4. Не ограничиваться проверкой DNS перед обычным requests-запросом: спроектировать привязку проверенного адреса к соединению с сохранением hostname/SNI/проверки сертификата. Тестировать DNS rebinding. Через HTTP CONNECT прокси локальная проверка DNS не доказывает адрес на стороне прокси: обеспечить контроль назначения либо отклонять маршрут, для которого гарантия невозможна; не заявлять полной защиты без этого.
5. Ограничить потоковую загрузку количеством байт до декодирования, включая распакованное тело. Ошибки политики не повторять и не обходить переходом с прокси на direct. Сетевые ошибки сохраняют существующий fallback.
6. Не отключать TLS-проверку автоматически. Существующий `sub_insecure` показать как отдельное явное исключение и не смешивать с разрешением LAN/HTTP.

## Зависимости и порядок выпуска

- Этап 0 → задачи 1–5 → отдельный выпуск исправлений безопасности.
- Задача 2 → 6 и 9; задача 7 → 8; задачи 3 и 8 → 11.
- Задача 8 учитывает новые настройки DNS, версии геобаз и логирование из задач 10–12; после их добавления расширить snapshot-тесты.
- Задача 4 может потребовать отдельного обновления xray; совместимость решается до объединения, не в конце релиза.
- Задачи 10–13 → выпуск улучшений настройки и диагностики.
- Задача 14 → самостоятельный выпуск уведомлений об обновлениях. Задача 15 не блокирует остальные и стартует после появления доверенной release-инфраструктуры.
- VK-план зависит от защиты логов, URL, snapshots и безопасного управления процессами; обратно общий план от VK не зависит.

Выполнить `make test-cov`, `make lint`, `make format-check`, `make test-gtk`, `make test-tray`, `git diff --check`. Проверить сборку AppImage, открытие старого профиля/настроек и сохранение данных после обновления.
